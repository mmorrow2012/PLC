**Decisions:**
- Wrote `parkingGateLogic.st` as a single `PROGRAM ParkingGateLogic` POU with seven ordered rung blocks (safety interlock, timer pre-evaluation, gate sequencer, stuck-gate watchdog, stuck-gate recovery, mutual-exclusion guard, final safety enforcement) evaluated in that fixed priority order every scan, then ported it 1:1 into a pure `runParkingGateLogic()` function in `src/plc/gateLogic.ts` (section numbers match) so the two sources can be diffed against each other and stay in sync, following the same pattern used in the sibling `01-conveyor-system` and `02-three-tank-liquid-level-control` projects.
- Modeled the `IDLE → OPENING → OPEN → CLOSING → CLOSED → IDLE` sequence as an `INT` `GateState` with named constants (`ST_IDLE` … `ST_CLOSED`) rather than five separate booleans, so the mutually-exclusive-state invariant is structural rather than something that has to be defensively checked. `CLOSED` is implemented as a genuine one-scan transient state (per the prompt's explicit `CLOSED → IDLE` arrow) that falls through to `IDLE` unconditionally on the following scan.
- Implemented the stuck-gate watchdog as two independent `TON` timers (`Tmr_WatchdogOpen`/`Tmr_WatchdogClose`), each gated on its own state, rather than one shared timer — this way a `CLOSING → OPENING` obstruction reversal gets a fresh full `T_WatchdogTimeout` window for the return trip instead of inheriting elapsed time from the aborted close, which better matches "max allowed time for a full open/close travel" in the prompt.
- Interpreted "require manual acknowledgement (via `PB_ManualOpen`/`PB_ManualClose`) to resume" as a hold-to-jog recovery: while `Alarm_StuckGate` is latched, holding either pushbutton drives the corresponding motor directly (bypassing the frozen sequencer) until the matching limit switch is reached, at which point the alarm clears and the sequencer resumes from `OPEN` or `IDLE`. This gives the operator a real recovery path (drive the gate to a known position) rather than a reset that leaves the gate physically stranded mid-travel.
- Reused `PB_ManualOpen`/`PB_ManualClose` for three duties documented in `PLC_LOGIC.md §2`: (1) normal-operation manual override (rising-edge transition `IDLE→OPENING` / `OPEN→CLOSING`), (2) E-Stop fault acknowledgement (rising edge, gated on `E_Stop` currently healthy — same pattern as the conveyor project's `Cmd_ManualReset`), and (3) stuck-gate jog (held level). Rising-edge duties use `R_TRIG`s; the jog duty reads the raw level directly.
- Discovered mid-implementation that modeling the pushbuttons as level-held commands (needed for jogging) broke a fast UI click: a `mousedown`+`mouseup` pair can both land inside the same 50 ms scan interval and cancel out before the engine ever reads `true`. Fixed by giving `ControlPanel.tsx` a `MIN_PB_HOLD_MS` (80 ms) minimum-release delay — asserting on press, releasing on a short timer after release — verified with a Playwright smoke test that reproduced the missed-click and confirmed the fix (both a fast click for E-Stop acknowledgement and a held press for stuck-gate jog now work correctly).
- Built `gateSimulation.ts` as a small, explicitly-separated physical-process model (0–90° arm angle, 3 s nominal full-travel time, comfortably inside the 8 s watchdog window) plus a simulation-only `gateJammed` flag (toggled from the HMI's "Mechanical Jam" control) that freezes the arm regardless of motor output, so the watchdog/stuck-gate path can be demonstrated on demand instead of only after a real 8 s stall.
- `Visualizer.tsx` renders the gate arm as an SVG line rotating from horizontal (0°, blocking) to vertical (90°, raised) driven directly by the simulated angle, the traffic light as two circles keyed off `Light_Red`/`Light_Green`, a pulsing buzzer indicator keyed off `Buzzer`, a dashed red obstruction beam when `Sensor_Obstruction` is active, and full-panel overlays for E-Stop trip (red, always-on) and stuck-gate (orange, distinct from the E-Stop overlay so the two fault types are visually distinguishable).
- `CodeViewer.tsx` imports `parkingGateLogic.st` via Vite's `?raw` loader (added `vite-env.d.ts`, absent from the scaffold) and highlights the live-executing rung block(s) via Monaco decorations keyed off store state — the safety/interlock sections highlight red during an E-Stop or stuck-gate fault, the sequencer highlights green whenever the engine is scanning, and the timer block highlights blue while `OPENING`/`CLOSING`.
- Verified end-to-end behavior with a headless Chromium Playwright smoke test against the Vite dev server, covering: vehicle arrival → auto-open → auto-close-after-departure → `IDLE`; obstruction-triggered reversal during `CLOSING`; E-Stop trip/restore/acknowledge with motors correctly held off until the explicit ack; and jam → watchdog timeout → `Alarm_StuckGate` latch → un-jam → held manual jog → recovery to `OPEN`. Confirmed via screenshots that all four HMI overlays (E-Stop, stuck-gate, fault-latched banner) render as intended.

**Trade-offs / deviations from prompt:**
- The prompt's I/O table does not include a dedicated "reset" input separate from `PB_ManualOpen`/`PB_ManualClose`; both the E-Stop fault clear and the stuck-gate acknowledgement reuse those two pushbuttons (documented in `PLC_LOGIC.md §2` and `ARCHITECTURE.md §4`) rather than inventing an unrequested `PB_Reset` tag.
- `gateJammed` (a simulation-only mechanical-failure flag, not a PLC I/O tag) was added so the 8 s watchdog timeout and stuck-gate recovery path can be exercised from the HMI without physically waiting out a healthy 8 s open/close cycle every time — called out explicitly in `ARCHITECTURE.md §5` as plant simulation, not control logic, matching how the sibling three-tank project documented its own simulation-only additions.
- The gate-arm's full 0–90° nominal travel time (3 s) is a simulation constant not specified in the prompt; chosen so a normal open/close cycle completes well inside the 8 s watchdog window while still being fast enough to observe interactively.
- `PB_ManualOpen`/`PB_ManualClose` are modeled as held-contact levels rather than the single-scan "pulse, then auto-cleared by the engine" pattern used for `Cmd_Start`/`Cmd_Stop` in the conveyor project, because the stuck-gate jog genuinely needs a multi-scan hold; the `MIN_PB_HOLD_MS` release delay in `ControlPanel.tsx` is a UI-layer compensation for that choice, not a change to the PLC logic itself.
- Forced I/O overrides are limited to `Sensor_GateOpenLimit`, `Sensor_GateClosedLimit`, `Motor_GateUp`, `Motor_GateDown`, `Light_Green`, and `Light_Red` — `E_Stop` and the vehicle/obstruction sensors already have dedicated toggle controls in the "Field Simulation" panel, so they're intentionally left out of the generic force list to avoid two competing controls for the same tag.
