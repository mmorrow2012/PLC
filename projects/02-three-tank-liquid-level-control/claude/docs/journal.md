**Decisions:**
- Implemented `threeTankLogic.st` as the canonical control-logic definition (overflow latch → E-Stop interlock → sequencer → output mapping → tower-light bitmask), then ported it 1:1 into a pure `evaluateScan()` function in `softPlcEngine.ts` so the TypeScript and ST sources can be diffed against each other and stay in sync.
- Kept `evaluateScan()` free of timing and store concerns; `SoftPlcEngine` wraps it in a `window.setInterval` loop that reads/writes the Zustand store, matching the "reads inputs, executes logic, updates outputs" scan-cycle description in the issue.
- Modeled the scan loop as always-running (started once on app mount, never stopped by Start/Stop), since a real MAST task cycles continuously regardless of process state — `Start_PB`/`Stop_PB` only drive the sequencer's `IDLE` vs. running state, not the scan itself.
- Added a small, explicitly-separated `simulatePlant()` linear tank model inside `softPlcEngine.ts` (fill/transfer/drain rates in %/s, plus a constant downstream draw from Tank C) because there is no physical process behind a browser demo — without it the analog levels would never move and the sequencer/visualizer would be inert. This is plant simulation, not control logic, and is documented as such in `ARCHITECTURE.md`.
- Extended the Zustand store's `PlcForces` (I/O forcing) so any of `LT_TankA/B/C` can be pinned to an operator-set value and excluded from the plant simulation — this is how the HMI's "manually nudge analog level inputs for testing" requirement works without the simulation instantly overwriting a test value, and it mirrors Control Expert's real I/O forcing feature.
- Implemented `Start_PB`/`Stop_PB` as one-shot pulses (`startPbPulse`/`stopPbPulse`) consumed once per scan by the engine, matching real momentary-pushbutton semantics rather than a toggle.
- Built `Visualizer.tsx` as a single inline SVG (three tanks, pump/valve indicators, tower light, setpoint reference lines, a full-canvas red pulse overlay on `Alarm_Overflow`/E-Stop) so the whole cascade is visible and animated at once rather than as separate readout cards.
- Wired `CodeViewer.tsx` to import `threeTankLogic.st` via Vite's `?raw` loader and highlight the source line corresponding to the PLC's current scan outcome using a Monaco decorations collection, satisfying "read-only execution indicators" with something that actually reflects live state rather than a static badge.
- Verified end-to-end behavior with a headless Chromium smoke test (Playwright) against the Vite dev server: confirmed the sequencer advances `IDLE → FILLING_A` on Start, Tank A's level animates upward, the code viewer's highlighted line tracks the state, and tripping E-Stop immediately shows the red alarm overlay, "E-Stop Active" banner, red tower light, and the corresponding `EStopTripped` branch highlighted in the ST viewer.

**Trade-offs / deviations from prompt:**
- The prompt's overflow-protection requirement only specifies forcing `Pump_Fill_A`/`Pump_Transfer_AB` to `FALSE`; it does not state what `Valve_Drain_BC_Pos` should do. Chose to drive the BC drain valve fully **open** during a latched overflow alarm (rather than closed or left as-is) as a protective measure that actively relieves Tank B toward Tank C. This only applies to the overflow case — the E-Stop interlock explicitly forces the valve to `0.0` per the prompt's requirement 4, which is followed literally.
- `SP_LevelA_High`/`SP_LevelB_High` were specified as cutoff setpoints but the prompt does not define a low-level setpoint for ending `DRAINING_BC`. Added an internal constant `TANK_B_DRAINED_THRESHOLD := 5.0` (not exposed as an HMI-adjustable setpoint) so the cycle can complete and return to `IDLE`; documented in `PLC_LOGIC.md`.
- The proportional drain-valve controller uses a fixed gain constant `VALVE_PROPORTIONAL_GAIN := 5.0` (`Valve_Drain_BC_Pos := Kp * (LT_TankB - SP_LevelB_Target)`, clamped 0–100%) since the prompt asked for simple proportional control without specifying a gain.
- Interpreted "manual reset (via Start_PB after alarm acknowledgement)" as: the field condition must clear AND a `Start_PB` press is required, which returns the sequencer to `IDLE` (not directly back into `FILLING_A`) — a second `Start_PB` press then begins a fresh fill cycle. This matches standard two-step industrial practice (acknowledge/reset, then start) more closely than auto-resuming mid-cycle with stale tank levels.
- Tank A/B/C are treated as equal capacity for the demo plant simulation (flows expressed as %/s rather than volumetric units), and Tank C has a constant simulated downstream draw (1.5%/s) that is not part of the specified I/O — without it Tank C would only ever fill and the demo would not be able to cycle repeatedly. Both are called out as simulation-only additions in `ARCHITECTURE.md`, separate from the control logic itself.
- Added `src/vite-env.d.ts` (`/// <reference types="vite/client" />`), absent from the original scaffold, so the `?raw` import used by `CodeViewer.tsx` type-checks under `tsc`.
- Ran `npm install` and `npm run build` inside `code/` to confirm a clean production build (0 TypeScript errors, 0 vulnerabilities), and additionally smoke-tested the running app in headless Chromium via Playwright to verify actual runtime behavior (sequencer transitions, animated levels, alarm overlays) beyond what type-checking alone would catch.
